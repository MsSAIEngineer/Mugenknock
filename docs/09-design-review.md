# 09. 設計レビュー（2026-10-01）

フロント・バックエンドの設計を、次の4つの目的に照らして批判的にレビューしたもの。

1. 本番に近い形式の問題を**早く演習できる**
2. **苦手を把握して、その部分を詰められる**
3. **運営費を安く抑える**
4. 問題生成・確認スクリプトを**効率的に回す**（現状 Claude の制限で回せていない）

コード品質の課題（巨大ファイル・`any`・ESLint 未稼働など）は
[08-refactor-plan.md](08-refactor-plan.md) にあるので、ここでは重複させない。
**すべての指摘は実測に基づく。** 推測の箇所はそう明記した。

## 2. 詳細

### 1.1 出題APIが運用メタデータを返している（優先S）

`GET /questions` は DynamoDB の項目をそのまま返している。実測:

```
返却フィールド: choiceExplanations, choices, choicesEn, correctAnswerCount,
  correctAnswerIndices, correctAnswers, createdAt, domain, examType, explanation,
  explanationEn, formatCheckedAt, isMultiple, linebreakCheckedAt, questionId,
  questionText, questionTextEn, translationCheckedAt, updatedAt,
  validityCheckedAt, validityEditLog  ← 21個
```

このうち UI が使うのは10個程度。`validityEditLog`（修正前後の全文）は1問あたり
**1.7〜2.9KB** あり、30問のセッションなら **50〜90KB** が完全な無駄になる。
`questionTextEn` / `choicesEn` / `explanationEn` は廃止済みの英語対応の残骸
（[08-refactor-plan.md](08-refactor-plan.md) E-1）。

**対処（実施済み）**: 公開の2ルート（`GET /questions` / `GET /questions/:id`）から内部メタデータを
落とす（`stripInternalFields`）。実測: **1問 10,203B → 4,466B（56%減）、10問取得 88,097B → 42,161B（52%減）**。
残った項目の値は完全に同一。UI が読まないことは、フロントの全参照を grep し、演習を最後まで通しで
操作して（解説・正誤表示・結果画面）確認した。

> **訂正**: 当初このレビューに「`ProjectionExpression` を付ければ DynamoDB の読み取り量も減る」と
> 書いたが**誤り**。DynamoDB の読み取り容量（RCU）は、射影した属性ではなく**アイテム全体のサイズ**で
> 課金される。射影で減るのは Lambda への転送量とメモリだけ。今回の対処が減らすのは
> **クライアントへの転送量**で、DB の読み取りコストは変わらない（元々月$0.5 程度なので影響は小さい）。

### 1.2 `/questions/public` が死んだまま1.18MBを返す（優先S・削除済み）

フロントからの参照は**0件**（`grep` で確認）。にもかかわらず実装は `limit` に未対応で、
資格の全問を返す。実測: `?examType=SAA&limit=5` に対して **1,177,395B**。

返却フィールドは絞られている（`validityEditLog` は含まない）ので §1.1 の手本にはなるが、
エンドポイント自体は**削除した**。

> **確認の経緯**: 実装前に本番ログを調べると、直近30日で `/questions/public` を含む行が**21,181件**あり、
> 「呼び出し元ゼロ」という前提が崩れかけた。日別に見ると 9/19 までが大量で **9/20 以降は0件**
> （SEO ページを全撤去した日と一致。ビルド時に4,000ページ分が叩いていた）。唯一の例外は 10/1 の1件で、
> User-Agent・クエリがレビューで私が叩いた `curl` と一致した。つまり現在は誰も使っていない。
> 削除後は `/questions/:id` に流れて 404 になる。

### 2.1 苦手の粒度が粗すぎる（優先S・最も重要な製品課題）

現状の苦手分析は**ドメイン単位**（SAA なら4個、CLF なら4個）。

```
Stats 画面 → ドメイン別正答率を低い順に表示
Focused モード → 正答率80%以下のドメインから出題
```

問題は、1ドメインが試験の20〜34%を占めること。
「セキュアなアーキテクチャの設計が60%」と言われても、
**IAM が弱いのか、KMS が弱いのか、VPC が弱いのかが分からない**。
これでは「苦手を詰める」という目的を満たせない。

`/users/me/weak-questions` は問題単位で返すが、これは「個別の問題を間違えた」記録であり、
**概念の弱点ではない**。同じ概念の別の問題が出れば、また間違える。

**対処の方向**（どれを採るかは要相談）:
- a. サービス単位のタグを整備して（§2.2）、その粒度で集計する
- b. 既存の `choiceExplanations` から「誤答時にどの選択肢を選んだか」を使い、
     誤解のパターンを出す（例: 「S3 と EBS を混同している」）
- c. 当面は「ドメイン × 正答率」に加えて「よく間違える問題に出てくるサービス名」を
     単純な文字列集計で出す（タグ整備より軽い）

### 2.2 タグデータが混沌としている（優先A）

`QuestionTagRelations` は3,137件・313種のタグがあるが、中身が統一されていない:

| 種類 | 例 |
|---|---|
| ドメイン名（表記ゆれあり） | 「組織の複雑さに対応する設計」と「組織の複雑さに対応したソリューションの設計」 |
| 短縮形との重複 | 「セキュリティとコンプライアンス」(107件) と「セキュリティ」(63件) |
| サービス名 | S3(31) / EC2(26) / Lambda(17) / VPC(15) |
| 英日混在 | 「コスト最適化」と `Cost Optimization` |
| 内部ID | `dop-cloudformation` / `dop-cdk` |

さらに約150種が**1問にしか付いていない**。カバレッジも3,137/4,902 = 64%。

`Tags` テーブルに至っては12件（CLF/SAA/SAP のみ）で、実質使われていない。

**この状態では §2.1 の分析に使えない。** 整備するなら、
ドメイン名タグは廃止（`domain` フィールドと二重管理）、サービス名タグに一本化、
が筋だと思う。

### 3.2 監視スクリプトが監視対象より高い（優先A）

Cost Explorer の API は **1リクエスト$0.01**。2026-09 の請求で $0.75 を占めており、
月75回ほど呼ばれている計算になる。呼び出し元は `backend-health-check.sh`。

監視対象の DynamoDB が月$0.51 なので、**監視のほうが高い**。
日次1回（月$0.30）に落とすか、コスト確認は手動のときだけにする。
（このレビューで私が1回叩いた分も$0.01かかっている。）

### 4.1 構造チェックをLLMにやらせている（優先S）

02 の検証プロンプトには約20の確認観点がある。そのうち次は、
**全4,902問を調べて違反が0件**だった（Jev 実験のときに測定）:

```
correctAnswers が choices と完全一致     違反 0件
choiceExplanations の件数が choices と一致  違反 0件
isMultiple フラグの整合                 違反 0件
選択肢の記号接頭辞（「A. 」等）          違反 0件（前処理で除去済み）
```

これらは**Python で確実・無料・一瞬**に判定できる。
にもかかわらず毎回プロンプトに含め、モデルに確認させている。

効果の見積もり（推測）: プロンプトが短くなる分の入力削減は小さいが、
**モデルが見る観点が減ることで1問あたりの推論時間が下がる可能性**がある。
現状は修正0件のチャンクでも5問に198秒かかっている。

**対処**: 前処理（すでに `choices` のラベル除去で実績がある箇所）に
構造チェックを集約し、プロンプトからは該当する観点を削る。
違反が出たら Python が直接直すか、その問題だけ Claude に回す。

### 4.2 固定ルールを1バッチで6回送信（優先A）

02 の確認観点ヘッダは4,881文字（約2Kトークン）。`CHUNK_SIZE=5` / `BATCH_SIZE=30` なので
**1バッチで6回**送られ、固定部分だけで約12Kトークンになる。

ただし入力の主役は問題本文（5問で約6Kトークン）なので、
チャンクを5→15にしても入力削減は17%程度（推測）。
**単独では効果が小さい。** §4.1（観点を減らす）と併せて初めて効く。
チャンクを大きくすると1回の出力が増えてタイムアウト risk も上がるため、
変えるなら実測しながら。

### 4.3 再検証が一巡4か月（優先A）

実測: 19.4問/回。hook は1日2回なので約40問/日。全4,902問を一巡するのに**約4か月**。
実際、最終確認日の中央値は7週間前、最古は5か月前（2026-05-07）。

ここで問うべきは「**全問を定期的に再検証する必要があるか**」。
問題の内容は勝手には変わらない。再検証に意味があるのは次の場合だけ:

- 検証ルールが変わった（例: 2026-08-20 の選択肢括弧ルール）
- AWS の仕様が変わった（サービス廃止・上限値の変更）
- その問題が編集された

**対処の案**: 「最終確認日が古い順」ではなく、
「**ルール改定日より前に確認された問題**」を優先する。
ルール改定がなければ再検証の必要は薄く、新規生成に枠を回せる。
今の実装は `validityCheckedAt` の昇順なので、ルール改定日を持たせれば実装は小さい。

### 4.4 41%の実行がレート制限で打ち切られる（優先B）

41ログ中16回で「レート制限を検出」。成果はチャンク単位でDBに反映済みなので
データは壊れないが、枠の使い方としては非効率。

現状は枠が尽きるまで走らせて打ち切る方式。`-D`（終了時刻）で区切ってはいるが、
**1チャンク＝5問に中央値276秒**かかるため、残り時間から処理可能なチャンク数を
見積もることができていない。

実測値（修正0件で198秒、修正1件ごとに+58秒）が分かったので、
残り時間から逆算してチャンク数を決められる。ただし優先度は低い
（打ち切られても損失は少ないため）。

### 5.1 CLAUDE.md が古く、開発速度を縛っている（優先S）

CLAUDE.md にこう書いてある:

> このサイトは静的ページが4000件超あり、ビルドには**数分〜10分程度**かかる

実測は**1.5〜2分**（直近10回: 84〜137秒）。4,000ページを生成していた
SEO 用の動的ルート（`/questions/[examType]/[questionId]` 等）は
AdSense 撤去時（`32ba3de` / `faaf0c7`）に**すべて削除済み**で、
今は `page.tsx` が22個、`generateStaticParams` は0件。

この古い記述のせいで、「ローカルビルドは重いので避ける」「並行ビルドは厳禁」という
過剰に慎重な運用になっている。実際には2分で終わるので、
ローカル検証をもっと気軽にやってよい。

同様に、`cf-deploy-status.sh wait` の待機上限20分も、実測2分に対して過大。
（安全側なので実害はないが、根拠は更新しておくべき。）

### 5.2 GSI の `ALL` 射影（優先C = やらない方がよい）

`examType-index` は `ALL` 射影なので、`validityEditLog` を含む全フィールドが
GSI にも複製されている（25.5MB）。書き込みのたびに2倍の WCU を消費する。

教科書的には `INCLUDE` 射影に絞るべきだが、**DynamoDB は既存GSIの射影を変更できない**
（作り直しが必要）。そしてコスト影響は月$0.5の一部でしかない。
**手間に見合わないので、やらないことを推奨する。**
§1.1（APIの返却フィールドを絞る）だけで、速度の目的は達成できる。

### 5.3 dev/prod のテーブル分割が中途半端（優先B）

`SPLIT_TABLES` で分割されているのは6つ（`Sessions` `UserAnswers` `UserQuestionStats`
`UserTagStats` `UserPoints` `EncyclopediaUnlocks`）。一方 `Questions` は dev/prod 共通。

結果として「スクリプトで問題を触ると本番に直撃する」状態になっている。
2026-09-30 の幽霊行（本番で500を起こしていた）も、
dev の夜間バッチが本番データを壊した例だった。

統一するか（全分割 or 全共通）、せめて
**「`Questions` は共通＝本番直結」をもっと目立つ形で明示**したい。
現状 CLAUDE.md には書いてあるが、1行だけで埋もれている。
