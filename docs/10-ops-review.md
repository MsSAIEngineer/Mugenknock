# 10. 運営の仕組みのレビュー（2026-10-27）

サイトを**運営する仕組み**を、定番の考え方に照らしてレビューしたもの。
対象は、リポジトリとコミットの管理、変更の出し方、環境とデータ、問題の生成・検証・監査、
夜間の運用、管理画面。フロントとバックエンドの設計は [09-design-review.md](09-design-review.md)、
コード品質は [08-refactor-plan.md](08-refactor-plan.md) にあるので、ここでは重ねて書かない。

**前提は「一人で運営していて、AWS 代が月 $3」であること。** 大きな組織向けの定番は、
そのまま当てはめると手間ばかり増える。採った基準と、当てはめなかった基準を分けて書く。
**指摘は今回測った値に基づく。** 推測の箇所はそう書いた。

---

## 0. 結論

1. **土台は思ったより定石どおり。** 管理者の権限はサーバ側で判定しているし、書き込み時の不変条件、
   問題テーブルのバックアップ、毎晩の canary、docs と specs の分担はそろっている。作り直す必要はない。
2. **いちばん大きな穴は「AI の判断を、人が確かめる経路がない」こと。** 生成と検証が同じモデルで、
   検証が直した正解はそのまま出題される。監査の指摘は2か月以上、誰も見ていない。
   問題の正しさがこのサイトの価値なので、ここに手を入れるのがいちばん効果が大きい。
3. **次に、壊れたときに戻せない所がある。** ユーザーデータのテーブルにバックアップがなく、
   Lambda には「1つ前に戻す」手段がない。どちらも手間は小さい。

## 3. よくできている点（直さなくてよい）

- **管理者の判定がサーバ側にある。** `/admin/*` は Lambda が Cognito の ID トークンを検証し、
  メールの許可リストと照らす。Cognito はメールの変更を確認前に反映しない設定
  （`AttributesRequireVerificationBeforeUpdate`）なので、メールを書き換えて管理者になりすますことはできない。
- **書き込みの不変条件を1か所で守っている**（`buildQuestionWriteFields`）。正解は index を正として、文言は作り直す。
- **問題テーブルは PITR が有効。** 削除が物理削除でも、35日以内なら戻せる。
- **毎晩 canary が本番を触って確かめ、日次レポートで知らせる。**
- **docs（今の姿）と specs（これからの姿）を分け、変更と同じコミットで docs を直す決まりがある。**
  一人運用でここまでそろっているのは珍しい。
- **トークンが律速だと分かったうえで設計している**（回復の直前に使い切る、検証にだけ WebFetch を残す）。
  `--model` と `--strict-mcp-config` の明示も、夜間バッチの挙動を固定する定石どおり。

### 4.1 生成と検証が同じモデルで、検証の確かさを誰も測っていない（S）

問題を作るのも、正しいかを判定するのも `sonnet` だ。LLM に採点させると、自分や同系のモデルの出力を
高く評価しやすいことが知られている（§1 の自己選好バイアス）。検証は WebFetch と AWS ドキュメントで
裏を取っているので、事実の誤りについてはこの偏りはかなり和らいでいるはずだ（推測）。
ただ、**検証がどれくらい当たっているかを測る仕組みがない**ので、和らいでいるのかどうかも分からない。

利用者からの通報は0件で、利用もまだ少ない（09 §0）。利用者の声で品質を確かめることも、今はできない。

**提案: 抜き取り検査を月1回する。**

- 検証済みの問題から、無作為に20問を選ぶ。
- 人（本人）が見て、誤りのある問題を数える。20問を見るのにかかるのは30分ほどの見込み。
- 結果を記録し、不良率の推移を見る。誤りが見つかったら、その種類を検証の観点に足す。
- 人の手間を減らしたいなら、別系統のモデルに独立に判定させ、検証と食い違った問題だけを人が見る形でもよい。

20問では不良率を細かく測れない。ただ「10%を超えているかどうか」くらいは分かるので、続ける価値はある。

### 4.2 検証が正解を変えても、そのまま出題される（S）

AI が直した 3,294問のうち、約22問は**正解そのものを変えている**。直したあとの問題は、別の目で確かめられないまま
出題プールに入る（次に再検証されるのは、一巡する約4か月後。09 §4.3）。正解の変更は、もし誤っていれば、学習者に間違いを覚えさせる。
いちばん害の大きい種類の変更だ。

**提案: 正解を変える修正だけ、人の承認を通す。**

- 管理画面の「修正案」（`fixProposalJson` → apply / reject）の仕組みはすでにある。
  正解の位置が変わる修正は自動で反映せず、修正案に回して、その問題は承認まで非表示にする。
- 件数は月数問なので、人の手間は小さい。
- 既に反映された約22問は、一度まとめて見直す。

### 4.3 人が見るべき指摘が溜まったまま流れている（A）

監査が「易しすぎる」「模試に向かない」と指摘した26問は、2026-08-16〜18 の指摘のまま、2か月以上手つかずだ。
監査は「人の判断が要る指摘」を出す設計なのに、人が見る順番がない。指摘が流れる仕組みは、ないのと同じになる。

**提案: 人が見るべきものを1つの列にまとめ、日次レポートで件数と一番古い日付を出す。**
対象は、監査の指摘、修正案（4.2）、通報、抜き取り検査（4.1）。古いものが溜まっていれば分かるようにする。
見ないと決めたもの（たとえば監査の指摘を当面扱わない）は、そう決めて指摘を外す。

### 4.4 生成指示の自動改良に、良くなったかの確認がない（A）

監査の `-i` と試験ガイドの更新は、生成指示（`instructions/*.txt`）を自動で書き換える。
書き換えたあとの指示で問題が良くなったのか悪くなったのかは、確かめていない。
プロンプトの変更は、決まった問題で前後を比べてから採用するのが定番だ（eval を先に作る）。

2026-10-27 から、書き換えは `chore(night):` のコミットとして git に残るようになった（[07](07-operations.md)）。
これで、何がいつ変わったかは追える。

**提案:** すぐに eval を作るのは手間が大きい。まずは、
**生成指示が変わった週の生成分を、4.1 の抜き取り検査で多めに見る**ところから始める。
監査（`-i`）を再開するときは、自動改良を「修正案を出すだけ」にし、反映は人が決める。

### 4.5 ユーザーデータのテーブルにバックアップがない（S）

`UserAnswers-prod`、`Sessions-prod`、`UserEntitlements-prod`（購入の権利）など8テーブルの PITR が無効だ。
誤った削除やバグで消えると、戻せない。8テーブルを合わせても 1.4MB で、PITR の費用は月1円にもならない。

**提案:** 8テーブルとも PITR を有効にする。テーブルを足すときの手順にも入れる。

### 4.6 Lambda を1つ前に戻す手段がなく、稼働中のコードがどの版か分からない（A）

`deploy-lambda.sh` は `$LATEST` を上書きするだけだ。本番で不具合が出たら、git で前のコードに戻して
デプロイし直すしかない。今いちばん速く戻せる手段がそれ、ということになる。
また、「git にはあるが prod に出し忘れた」事故（CLAUDE.md の出題ドメイン均等化の件）は、
**動いているコードがどのコミットかを記録していない**ことが根っこにある。

**提案:**

- デプロイのたびに `publish-version` し、`live` エイリアスを付け替える。
  API Gateway のステージ変数 `lambdaFn` を `awsquizHandler-prod:live` に変える（エイリアスへの呼び出し許可も足す）。
  戻すときは、エイリアスを1つ前の版に向けるだけで済む。
- 版の説明にコミットの SHA を入れる。
- 日次レポートで、dev・prod それぞれの SHA と develop・master の SHA の食い違いを出す。

### 4.7 テストはあるのに、どこでも自動で走らない（A）

`lambda/test`（出題の選び方・課金・決済の webhook など4本）と e2e は、手で走らせたときしか動かない。
直近60日の修正系コミットが 47% あることから見て（目安。§2 の注意を参照）、
手前で止められる不具合もあったと思われる（推測）。

**提案:**

- `deploy-lambda.sh` の最初に `node --test lambda/test/` を走らせ、失敗したらデプロイしない。
- GitHub Actions で、push のたびに `tsc --noEmit`・`lint:tokens`・`node --test` を走らせる。
  公開リポジトリでなくても、無料枠の範囲で足りる規模だ。

### 4.8 本番に出すまでの変更が大きい（B）

develop に30件・15日分が溜まっている。まとめて出すほど、壊れたときにどの変更が原因かを
切り分けにくくなり、戻す範囲も大きくなる（DORA の考え方）。
本番に出すたびに確認を挟む今の決まりは、一人運用では妥当だ。変えるのは「確認の単位」のほうだ。

**提案:** 小さな修正がまとまった時点で、こまめに本番へ出す（目安は数日に1回）。
確認で示す一覧が短くなるので、確認そのものも楽になる。

### 4.9 管理者アカウントに MFA がなく、夜間バッチも同じアカウントを使う（A）

管理者は、問題の削除、ユーザーの削除、お知らせの配信ができる。そのアカウントがパスワードだけで守られている。
さらに夜間バッチは、同じ本人のアカウントでパスワードログインしている。その結果、次の2つが起きる。

- 公開アプリのクライアントで `USER_PASSWORD_AUTH` を有効にしておく必要がある。
- 本人のアカウントに MFA を付けると、夜間バッチが止まる。

人とバッチが同じ鍵を使っていることが、MFA を付けられない原因になっている。

**提案:**

- 夜間バッチ用に、管理者の許可リストに入った専用ユーザーを作る。パスワードは SSM のまま。
  専用のアプリクライアントを作り、`USER_PASSWORD_AUTH` はそちらだけで有効にする。
- そのうえで、本人のアカウントに MFA（TOTP）を付ける。
- 将来は、バッチの書き込みを IAM 認証の別経路にする手もある。今は専用ユーザーで足りる。

### 4.10 管理操作の記録がない（B）

管理画面やバッチが問題を消したり書き換えたりしても、「誰が・いつ・何を」の記録が残らない。
AI の修正は `validityEditLog` に残るが、人の編集と削除は残らない。PITR で中身は戻せても、
何が起きたかを後から追えない。

**提案:** `/admin/*` の変更系 API で、操作者・対象・操作の種類を1行ずつ記録する。
CloudWatch Logs に構造化ログを出すだけでもよい。

### 4.11 夜間の処理が黙って止まっても気づけない（A）

夜間の各処理は失敗しても `|| true` で先へ進み、結果は日次レポートのメールで知る。
これは「失敗しても止まらない」ためには正しい。困るのは、**処理そのものが動かなかった日**だ。
日次レポートも同じ仕組みで送るので、PC が止まっていたりフックが外れたりすると、
レポートが届かないことでしか気づけない。届かないことには、気づきにくい。

**提案:** 「最後に成功した時刻」を見張る仕組み（dead man's switch）を1つ置く。

- 各処理の成功時刻を1つのファイルに書く。
- 外部の監視サービスに毎日「生きている」を送り、届かなければ通知させる。Healthchecks.io などの無料枠で足りる。

### 4.12 夜間の仕組みの定義が git の外に散らばっている（B）

夜間の処理は、次の4か所に分かれて定義されている。

- systemd のユニット（`~/.config/systemd/user/`）
- claude-timer のフック（`~/.config/claude-timer/hooks.d/` に4ファイル）
- 実行済みの印とフラグ（`~/.config/mugenknock/`）
- リポジトリのスクリプト

このうち git に入っているのはスクリプトだけだ。PC を入れ替えたり壊したりすると、
ユニットとフックを記憶から作り直すことになる。開発環境のバックアップも、今は手動でしか取っていない。

**提案:** ユニットとフックの定義をリポジトリ（例: `ops/systemd/`、`ops/hooks.d/`）に置き、
`install` スクリプトでリンクを張る。claude-timer 本体はすでにこの形（独立リポジトリ + `install.sh`）になっている。

### 4.13 複数のセッションが1つの作業ツリーを共有している（B）

CLAUDE.md には、作業ツリーの共有から起きた事故が2件記録されている
（`.next` を壊した件、作りかけを本番に出した件）。決まりで防いでいるが、決まりは忘れられる。

**提案:** 並行して作業するセッションは、`git worktree` で別の作業ツリーを使う
（Claude Code にも worktree で作業する機能がある）。夜間バッチの資産は 2026-10-27 から自分でコミットするので、
作業ツリーに混ざるものはもう少ない。

### 4.14 夜間の中核がシェルで書かれていて、テストできない（B）

夜間のスクリプトは計 9,922行で、1,000行を超えるものが3本ある。中に Python の heredoc が埋め込まれている。
シェルは、規模が大きくなると引数・エラー・文字列の扱いで壊れやすく、単体テストも書きにくい。
今回の作業でも、heredoc の中の `}` で抜き出しが壊れた。

**提案:** 一度に書き直す価値はない（動いているし、手間が大きい）。
**判断の入った部分**（重複判定、出題の選定、カタログの照合、レポートの集計など）を、
直すついでに Python のモジュールへ移し、テストを付ける。シェルは呼び出し役に絞る。

### 4.15 分割前の旧テーブルにデータが残っている（B）

dev/prod に分ける前の `Sessions`、`UserAnswers` など6テーブルに、データが残っている。
どこからも使われていなければ、誤って読み書きされる元になるだけだ。

**提案:** コードから参照されていないことを確かめ、エクスポートしてから削除する
（本番データの削除になるので、そのときに確認する）。

## 5. やらないほうがよいこと（C）

| 定番 | やらない理由 |
|---|---|
| GitFlow（release・hotfix ブランチ） | 一人運用では、ブランチを増やした分だけ手間と事故が増える。develop と master の2本で足りる |
| インフラを全部コード化する（CDK・Terraform） | テーブルと API はほとんど変わらず、月 $3 の規模に対して導入と維持の手間が大きすぎる。4.12 の「ユニットとフックを git に入れる」だけで、困る所は埋まる |
| `Questions` まで dev/prod を完全に分ける | 問題は1つの正があればよく、二重に持つと同期の手間が増える。PITR があるので、dev のバグで壊れても戻せる |
| 検証の全件を人が見る | 6,500問は人の手に余る。抜き取り（4.1）と、害の大きい変更だけ人を通す（4.2）で足りる |
